Запиши итоги текущей сессии в журнал `~/.lifeos/journal/`. Предлагай вызов проактивно: при логической паузе (переключение между задачами, длинная остановка), смене контекста (переход к другому проекту/теме), признаках усталости (сессия >3ч, сдвиг от задач к мета-вопросам) — как мягкое закрытие сессии.

Все пути берутся из `~/.lifeos/` (переопределяется env `LIFEOS_HOME`). Журнал и логи не привязаны к проекту — плагин user-scope, работает из любой папки.

## Инструкция

1. Выполни две команды параллельно:
   - `date '+%Y-%m-%d %H:%M %z'` — точное время с часовым поясом
   - `bash "${CLAUDE_PLUGIN_ROOT}/scripts/session-analyze.sh"` — метрики сессии (<0.5 сек)
2. Определи ISO-неделю из даты. Файл журнала: `~/.lifeos/journal/YYYY-WNN.md` (например `2026-W12.md`). Неделя: понедельник–воскресенье (ISO 8601). Файл создаётся скриптом записи автоматически.
3. **Краевой случай (смена недели):** если `session_start` из анализатора попадает в предыдущую неделю — запись пишется в файл **текущей** недели с пометкой `(начало в W{N-1})` в строке Сессия.
4. Проанализируй, что было сделано. Для каждого пункта: **что** изменилось, **зачем** (проблема/цель), **в каком контексте** (проект, область, домен).
5. **Не читай weekly-файл целиком** для поиска дубля. Скрипт `session_log_append.py` в режиме `--mode auto` сам находит блок по маркеру `<!-- session: ID -->` и делает insert/update.

## Формат записи

```markdown
### YYYY-MM-DD HH:MM

**Сессия:** начало HH:MM, промптов N, активное время ~Xч Yмин, пауз: K | параллельных сессий: M | локация
**Контекст:** [домен/область — например: Работа/продукт, LifeOS/инфраструктура, Личное/финансы]
<!-- session: SESSION_ID | name: Имя сессии | host: hostname -->

- [Контекст] Что сделано и зачем.
- [Контекст] Второй пункт...

Изменено: `файл1`, `файл2`
```

**Hostname** — `hostname -s` (трассировка машины: сессии локальны). **Имя сессии** — из `/rename` или `-n`; если не задано — предложить в конце (см. ниже).

## Контекст записи (главное правило)

Журнал — **единственный источник данных** для агентов верхнего уровня (обзор недели, персональный коуч): transcript им недоступен, они видят только журнал. Поэтому каждая запись должна позволять внешнему агенту понять домен/проект/область, заметить параллельные сессии, оценить продуктивность, учесть локацию и TZ.

**Строка «Контекст:»** — смысловая классификация («LifeOS/инфраструктура — трекинг сессий»), не техническая («писал bash»). **Пункты** — с контекстом в скобках при >1 домене. **Локация** — из анализатора (`location=`); `tz_changed=true` → TZ менялся (перелёт), отметить.

## Запись в журнал (атомарная, через session_log_append.py)

**Не используй Edit для вставки в weekly-файл** — параллельные `/session-log` из разных сессий дадут race condition. Вместо этого:

1. Сформируй готовый блок записи и запиши в `~/.lifeos/logs/session-log-payload-<session-id>.md`. **Перед Write сделай Read** этого файла (payload мог остаться от предыдущего вызова в той же сессии; Write fail'нется без предварительного Read). Если Read вернул ошибку «не существует» — сразу Write.
2. Вызови:
   ```bash
   python3 "${CLAUDE_PLUGIN_ROOT}/scripts/session_log_append.py" \
     --week-file "${SESSION_LOG_JOURNAL_DIR:-$HOME/.lifeos/journal}/YYYY-WNN.md" \
     --session-id <SESSION_ID> \
     --payload-file "$HOME/.lifeos/logs/session-log-payload-<SESSION_ID>.md" \
     --mode auto \
     --week-range "YYYY-MM-DD (Пн) — YYYY-MM-DD (Вс)"
   ```
   **Путь журнала** — env `SESSION_LOG_JOURNAL_DIR` (дефолт `~/.lifeos/journal`). Кто держит журнал в Obsidian-vault — указывает сюда vault-путь (тогда журнал виден в Obsidian и связан с заметками). Логи всегда в `~/.lifeos/logs` (технические, project-independent).
3. Скрипт берёт `flock` на `~/.lifeos/logs/session-log.lock`, ищет блок по `session-id`, делает insert/update, атомарно переписывает файл. Вывод: `mode=insert|update`. При `error:` — разобраться.
4. `--week-range` нужен только при создании нового weekly-файла (первая запись недели).

## Правила

- Время в заголовке — точное (из `date`), момент вызова.
- Строка **Сессия:** — метрики из анализатора. Недоступен — опустить, не блокировать запись.
- Маркер `<!-- session: ID | name: ... | host: ... -->` не удалять.
- Каждый пункт — что + зачем. Объём пропорционален сессии. Проекты — wikilinks. «Изменено:» — ключевые файлы.
- Пустая/тестовая сессия — не записывать.

## Обновление записи (повторный вызов в той же сессии)

Одна техническая сессия (один session_id) может иметь несколько вызовов. При обновлении: заголовок `###` → текущее время; **Сессия:** → обновить метрики; **Контекст:** → расширить; пункты → дописать новые; «Изменено:» → объединить.

## Фиксация в календаре (опционально)

Если задан env `SESSION_LOG_CALENDAR_ID` — после журнала зафиксировать **фактические блоки работы** в Google-календарь (тайм-блокинг). **Если переменная пуста — пропустить весь блок, журнал самодостаточен.**

Команда gws — из env `SESSION_LOG_GWS` (дефолт `gws`). Факт-блок: `summary` начинается с `✓`, `colorId: "2"`, `extendedProperties.private` несёт `sessionId`+`block`+`context` (идемпотентность + фильтрация по объекту работы).

**Объект работы (context).** Каждый блок привязан к объекту, над которым шла работа: проект/продукт/область/док-путь — любой элемент твоей системы. Claude знает его из сессии, пишет в строку **Контекст:** журнала и в `extendedProperties.private.context` события. Это ключ группировки при анализе многих сессий (время по проекту/объекту).

### Алгоритм блоков (ядро)

1. **Контекстные блоки.** Для каждого — контекст (проект/домен/область) и временные рамки по логу промптов.

2. **Время блока:**
   - **Старт** = первый промпт блока, конвертированный в текущий системный TZ, округлён ВНИЗ до 15 мин.
   - **Длительность** = block wall clock, округлена до 15 мин, минимум 15.
   - Пересечения допустимы (параллельные сессии — оба блока с реальным start/duration, не сдвигать).

   **Расчёт (block wall clock):** прочитать лог промптов `~/.lifeos/logs/claude-session-{id}.log` **через Read tool**. Разбить на непрерывные блоки: пауза >30 мин между соседними промптами = граница. Блок через полночь → разбить по дням. Длительность = `последний − первый промпт` + 5 мин, округлить вверх до 15. Один промпт в блоке → 15 мин.

   **Почему block wall clock:** `active_time` (сумма gaps <15 мин) занижает (не учитывает чтение ответов); полный wall clock завышает (включает паузы). Block wall clock = реальное рабочее время.

   **Конвертация TZ (при перелётах):** лог хранит ISO с offset (`...+0500`). Прочитать offset, определить текущий TZ (`date '+%:z'`/`'+%Z'`), сконвертировать старт (и дату) перед подстановкой в `start`/`end`. `date -j -f '%Y-%m-%dT%H:%M:%S%z' '<ts>' '+%Y-%m-%d %H:%M'`.

3. **Название блока** — кратко + ` (блок N)` при >1 блоке.

4. **Идемпотентность.** Перед вставкой найти события сессии:
   ```bash
   "$SESSION_LOG_GWS" calendar events list --params '{"calendarId":"'"$SESSION_LOG_CALENDAR_ID"'","privateExtendedProperty":"sessionId=<SESSION_ID>"}'
   ```
   Есть событие блока с тем же `sessionId`+`block` → `events patch`, нет → `events insert`.

5. **Запись:**
   ```bash
   "$SESSION_LOG_GWS" calendar events insert \
     --params '{"calendarId":"'"$SESSION_LOG_CALENDAR_ID"'"}' \
     --json '{"summary":"✓ {название}","start":{"dateTime":"YYYY-MM-DDTHH:MM:00<offset>","timeZone":"<TZ>"},"end":{"dateTime":"YYYY-MM-DDTHH:MM:00<offset>","timeZone":"<TZ>"},"description":"{контекст}\n{что сделано}","colorId":"2","extendedProperties":{"private":{"source":"session-log","kind":"fact","sessionId":"<SESSION_ID>","block":"N","context":"<объект: проект/продукт/область>"}}}'
   ```
   `<offset>`/`<TZ>` — текущего системного TZ. `end` = `start` + длительность.

6. **Спросить перед записью.** Таблица блоков (Блок | Контекст | Время | Длительность) + варианты: `1` подтвердить, `2` пропустить календарь (только журнал), `3` скорректировать.

### Правила календаря

- Календарь — ПОСЛЕ журнала (журнал primary). gws недоступен — не блокировать журнал.
- Факт всегда `✓` + `colorId: "2"` (отличие от плановых блоков без `✓`).
- Повторный вызов — patch по `sessionId`, не дубль.
- **Финал:** `Сессия зафиксирована. Журнал: ~/.lifeos/journal/YYYY-WNN.md. Календарь: N блоков, Xм.` Можно закрывать `/exit`. Если сессия не именована — отдельной строкой `/rename {предложенное имя}`.

## Авто-предложение имени сессии

При каждом вызове проверять имя (маркер `<!-- session: ID | name: ИМЯ -->`). Если `name` пуст/UUID — придумать осознанное короткое (≤6–7 слов, русский, по делу): `{Проект} — {задача}` / `{Область} — {что делали}` / `{Главный} + {N}`. `/rename` автоматически не вызывать — предложить готовую команду в финале. Предложенное имя записать в маркер.

## Понедельные файлы

`YYYY-WNN.md` (ISO 8601, Пн–Вс). Нумерация недель ISO (`date '+%V'`). Обратная хронология внутри файла (новые сверху).

## Решения (почему так)

- **Данные в `~/.lifeos/`, не в проекте:** плагин user-scope, хук срабатывает в любом проекте — привязка к `${CLAUDE_PROJECT_DIR}` плодила бы папки в случайных репозиториях. Канонический home-путь стабилен везде.
- **Понедельные файлы** вместо помесячных: месячный разрастается до сотен строк.
- **Duration = block wall clock**, не active_time (занижает) и не полный wall clock (завышает).
- **Округление до 15 мин**, блоки по дням, суффикс `(блок N)` при >1 блоке.
